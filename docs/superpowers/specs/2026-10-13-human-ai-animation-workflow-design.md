# Sprite Motion Studio 人机协作动画制作设计

日期：2026-10-13  
状态：用户已于 2026-10-13 明确确认本设计；功能尚待实施。  
范围：现有本地 Windows 工具的制作接口、验收流程、版本规则与配套 Skill。本文是设计规格，不是执行计划。

## 1. 目的与成功标准

将工具定位为人和 AI 共用的动画制作工作台：用户提供素材和目标，Codex 完成主要制作、自检及返工，用户在最后逐帧检查最终画面并验收连续播放，工具保存过程、管理版本并交付一致的正式产物。

成功标准是用户主要承担目标决定和质量验收，而无需为完成普通任务填写接口参数、编写 recipe、操作命令或亲自修正每个问题帧。用户仍可手工修改；人工逐帧确认不得省略。遇到素材缺失或制作无法继续时，Codex 可以提前提出具体问题和处理选项。

Skill、自动检查和 AI 抽样视觉检查用于减少可避免的错误，不承诺零错误。技术检查通过不等于美术验收通过；抽样未发现问题不等于所有帧无缺陷。

## 4. 分层与职责

采用“Codex + 配套 Skill → 本地 MCP / CLI → 共享制作服务 → 现有图像 Worker”的结构。GUI 从同一服务读取任务、候选和审核记录。

| 层 | 职责 |
| --- | --- |
| Codex / Skill | 理解目标，规划调用，读抽样画面，决定修复，汇总证据与不确定性 |
| MCP / CLI | 暴露可发现、结构化的业务操作与错误；不包含第二套制作算法 |
| 共享制作服务 | 校验参数、版本和项目归属，存储任务 / 候选 / 审核，执行确定性的状态转移 |
| 图像 Worker 与现有队列 | 抽帧、抠图、笔刷修正、合成、全帧技术检查和打包 |
| 验收工作台 | 用户逐帧对照、确认 / 标问题、播放验收和手工修正 |

工具不在后台替 Codex 运行 LLM。计算任务可继续执行；Codex 会话中断后，下一次读取持久状态再继续决策。继续使用现有任务队列和客户端租约机制，不新增调度平台。

## 5. 用户流程与任务要求

### 5.1 用户入口

典型请求：“把这个视频做成角色奔跑的透明序列帧。”

Codex 先读取素材信息、已有项目和角色预设。信息足够时直接执行；必须补充信息时集中确认主体、动作范围和输出规格。确认用途是形成制作任务，不要求用户批准每个普通工具调用。

任务要求至少记录：工作区 / 项目 / 动作、源引用与源哈希、主体 / 区域、片段范围、公共画布 / 锚点 / 比例、重采样风格、根轨迹类型、源时序或明确指定的时序变更、是否循环、交付格式及采样预算。

这些是内部记录字段，不是用户必须填写的表单。每项记录来源为用户要求、已确认预设或工具 / Codex 推导。项目 ID、源哈希、源时长、文件尺寸、采样预算和交付清单由工具填充；明确的单主体和未要求截取的片段使用整个输入；画布 / 锚点 / 比例等已有预设直接复用，没有预设则由 Codex 根据素材提出推荐值。仅对主体歧义、无法判断的动作 / 根行为、指定用途所需但缺失的尺寸或 PNG 时长等必要信息集中询问，不要求用户填写 recipe 或数值问卷。

信息足够时不额外询问；首次确有必要确认时最多一轮集中问题，并展示推荐值。之后只有新发现的具体阻断、素材歧义或用户改变目标才追加问题，记录原因，避免重复询问已知要求。

公共画布、锚点、比例和重采样复用角色预设；地面根和轨迹按动作保存。跳跃、下蹲、倒地不能直接将每帧最低像素当作地面根。主体或根行为不能可靠判断时，作为必要例外询问用户。

PNG 文件顺序在导入前明确展示并保存；有显式清单时使用清单，否则自然排序。PNG 缺源时长时，使用已确认预设 FPS；没有预设则集中确认一次，不伪称存在视频源时间戳。

### 5.2 制作与审核

1. 检查依赖、能力和工作区，创建 / 打开项目与动作。
2. 保留原件和完整源帧，进行抠图、修正和对齐。
3. 生成尚未公开审核的固定检查候选，再运行所有帧的技术检查。
4. 获取该候选的采样清单，进行有限视觉自检；修复改变内容时生成新的固定检查候选，并对新版重新检查。
5. 在哈希与内容身份仍一致的前提下，将已检查的候选发布到验收工作台，附其自检记录。
6. 用户在验收工作台逐帧确认，连续播放并记录播放验收；问题以版本化标注提交。
7. Codex 基于标注修复制作副本，提交新候选及影响报告。
8. 用户复审；全部条件满足后自动生成正式交付包。

用户手工修改也经过相同内容变更 / 新候选流程。修改按钮进入制作副本；正在审核的候选保持可回看，不以新画面悄悄替换旧画面。

## 6. 状态与最小数据模型

### 6.1 协作任务

在现有持久任务基础上增加轻量协作记录，关联现有 job ID，不新增图像执行队列。共享类型和 schema 放在 `packages/shared`。

协作状态为：

`preparing → producing → checking → awaiting_review → reworking → checking → awaiting_review → accepted → packaging → delivered`

另有 `needs_input`、`failed`、`cancelled`。失败 / 中断保留最近成功阶段、具体 job ID、错误和恢复位置。

低层抠图“计算完成但未被人工确认”与协作任务 `awaiting_review` 是不同事实。新流程中，抠图 job 完成表示计算产物可用，遮罩仍未审核；Codex 可以继续制作和草稿检查。只有提交固定候选时才进入人工验收阶段。旧 GUI 的未确认标识继续存在，不由 AI 自动改成通过。

### 6.2 持久记录

| 记录 | 必要内容 |
| --- | --- |
| 协作任务 | task ID、工作区 / 项目 / 动作、要求及其版本、状态、关联 job、当前制作修订、当前选定候选、接受代次、恢复点 |
| 候选 | candidate ID、父候选、任务要求版本、来源内容修订、固定帧 / 时序 / 参数、合成器与采样策略版本、全帧检查、自检、采样清单、生成时间 |
| 候选帧 | 稳定帧 ID、序列位置、源索引、源 / 遮罩版本及哈希、最终 PNG 哈希、有理数时长及其来源、实际应用变换及根位置 |
| 人工审核 | candidate ID、帧 ID / 内容身份、审核修订、待确认 / 通过 / 需修复、明确操作来源、时间、继承来源 |
| 问题标注 | issue ID、候选、帧 / 帧范围、区域、坐标系、问题文本、状态、对应修复候选 |
| 播放验收 | candidate ID、帧顺序 / 时长 / 画面组成的身份、用户明确确认、时间 |
| 交付 | candidate ID、正式产物位置、校验清单、交付状态、job ID |

内容身份从实际输入 / 输出字节和参数计算，不以文件名、mtime、缩略图或模型声称“检查过”代替。

## 7. 候选固定与审核规则

### 7.1 固定候选

提交时生成专属候选目录及清单，冻结全部最终透明 PNG、图集布局、顺序、时长和输出参数。源图 / 遮罩引用必须指向不可变版本；不能引用可被原位覆盖的编辑副本，必要时复制为候选专属文件。

固定先于检查：候选先以私有状态生成，完成技术与抽样检查后再公开提交。检查期间发生修改就生成新候选；不能在检查完旧画面后重新渲染一套新画面提交。内容清单和内容身份不可变，检查记录与人工审核作为独立附加记录保存。

候选产物由共享合成器产生。预览、逐帧确认和正式交付使用同一最终 PNG。MP4 和缩略图是辅助检查材料，不能作为最终透明帧的权威像素。

固定候选仍有文件完整性校验。候选文件丢失或被外部程序修改时拒绝批准 / 交付，保留错误证据，重新制作候选；不能就地修补并保留原批准。

### 7.2 制作修订与审核修订

制作内容变化增加内容修订；人工确认、问题备注和播放验收增加独立审核修订，不改变候选内容身份。确认按钮重复提交应幂等。

审核修改带预期审核修订和幂等标识，冲突时重新读取当前审核状态，不能用内容修订代替。接受记录保存选定候选、审核修订和接受代次；撤销必要确认、新增阻断问题或切换选定候选使该接受代次失效。非阻断备注不撤销帧批准，但发布前仍读取最新审核状态并校验接受条件。

现有项目 revision 可继续用于旧路径并发控制；新候选审核不调用会变更制作 revision 的旧 `reviewMask()` 来伪装新状态。旧路径与新候选路径的批准记录保持明确来源，不能将“旧遮罩 reviewed”直接迁移成“最终合成帧已经验收”。

新候选接受由其实际帧批准和播放验收决定，不要求用户在同一界面先逐帧批准遮罩、再逐帧批准最终帧。遮罩检查入口保留，最终帧确认涵盖用户对实际输出的决定。

### 7.3 人工确认与 AI 记录

AI 自检记录只说明技术结果、抽样范围、观察和修复；不能写入人工通过状态。

新制作 MCP / CLI 能读取审核状态、提交候选和修复问题，不提供伪造人工批准的制作参数。用户在 GUI 执行逐帧和播放确认，由独立审核入口记录；制作会话不能经旧 `/mask/review` 或 `/review/apply` 自行替代新候选验收。会话角色与入口校验由服务执行，不能只靠 Skill 的文字约束；调用方传 `actor: human` 不构成权限凭据。

当前 Bearer 与 GUI Cookie 使用同一个服务 token，不能据其来源判断角色。新流程由服务签发区分制作 / 审核能力的会话：CLI / MCP 服务描述只提供制作凭据；桌面启动器初始化的 GUI 会话通过 HttpOnly Cookie 获得审核能力，审核凭据不出现在制作工具结果或 CLI 服务描述中。制作凭据不能请求升级为审核凭据；原共享服务 token 不能直接写新候选审核。现有本机启动和凭据管理实现扩展这些能力，不新增账户系统。

这是防止制作流程误批准的权限边界，不声称能证明坐在电脑前的人的身份或判断质量。现有本机鉴权、Origin / Host 与文件访问边界继续保留。

## 8. 返工与复审影响

以父候选的稳定帧 ID 和内容身份比较新候选；不只比较全局 project revision。

| 变更 | 必须处理的审核范围 |
| --- | --- |
| 单帧遮罩 / 位移 / 旋转 / 透明度 / 局部偏移 | 该帧重新确认；标记相邻帧为衔接复审范围；循环动作还包含受影响的首尾衔接；播放验收失效 |
| 根轨迹关键帧变化 | 重新计算受插值与端点保持影响的全部帧；范围包含实际变化段，不只包含关键帧本身 |
| 公共画布 / 锚点 / 比例 / 重采样 | 所有受该角色预设影响的动作候选标记需要更新；新候选全部相关帧复审 |
| 帧顺序、选择、时长、循环要求变化 | 播放验收失效；变化位置及相邻连接范围复审；重新核对按序号表达的根轨迹 / 偏移对应关系；全局重排扩大到全序列 |
| 源 / 遮罩文件字节变化 | 所有引用变更输入的帧重新确认；不能用旧路径或相同文件名绕过 |
| 仅问题文字 / AI 检查记录变化 | 不改变像素与时序，不使已有帧批准失效 |
| 影响无法可靠计算 | 相关动作全部复审，报告原因 |

未受影响的帧批准可以显式继承，保留父候选、原确认和继承依据。需要复审的相邻帧即使像素相同，也不能在提示衔接问题的同时自动显示“无需检查”。

公共预设更新不会原位改写历史固定候选：它更新制作副本并产生新候选。当前任务不能把旧候选批准自动转成新候选批准。历史版本可以回看；历史交付只能由用户明确选择该已验收版本。

未解决的阻断问题阻止接受。用户明确接受源素材已有的视觉缺陷时记录接受范围；空帧、越界、输入损坏等必需技术条件仍不能通过例外绕开。

## 9. 全帧技术检查与抽样视觉检查

### 9.1 全帧技术检查

覆盖每个输出帧：序列数量与源映射、顺序、时长合法性、哈希 / 文件完整性、公共画布、实际渲染 Alpha 非空、几何越界和预设一致性。保留有理数源时序，不将预览视频 FPS 当作权威时长。

检查类别分为阻断错误与提示。Imported PNG 的合法半透明像素继续可用，不为得到“不透明核心”而强制改变 Alpha。自动抠图的低置信噪声仍遵循严格校验；不得把所有可疑信息当作 AI 能自动确定的美术缺陷。

### 9.2 视觉采样

工具生成确定性的采样清单和可读预览，Codex 按清单观察，不将前 8 / 32 帧摘要当采样策略。采样 ID、选择原因、候选身份及实际观察结果写入自检记录。

每个内容候选的默认预算为 `B = min(12, max(1, floor(N/2)))`，N 是输出帧数。用户预设可降低上限，不由 Codex 自行提高到全帧覆盖。N=1 时只能检查唯一帧；N>1 时 B<N。

选择规则按以下顺序执行，重复帧去重，总数不超过 B：

1. B≥2 时保留首尾；B=1 时选最高优先级风险帧，无风险选首帧。
2. 风险补充最多 4 帧，并受剩余名额限制。优先级依次是用户指出的修复帧、其衔接邻帧 / 循环边界、工具警告严重度、其他变化线索；同级按序列位置排序。必留首尾不被替换。
3. 常规样本（包含首尾）最多 8 帧，用剩余名额按累积时长均匀取样；相同时刻选较早帧。已选帧重复时寻找最近未选帧，同距选较早帧。无风险补充时不为用满 12 的上限而额外取样。

预算按候选计算。一次候选内对同一帧的源图 / Alpha / 背景切换仍算同一帧，不获得额外取样名额；缓存或复读不会扩充集合。返工新候选有自己的 B，但优先复用内容身份完全相同的已有观察证据，明确标注其来源，不反复读取未变化画面。预算限制的是每轮视觉覆盖，并非承诺整个返工任务只耗费固定模型调用或时间。

自动技术检查可提供空帧、越界等实际异常；面积 / 边界变化、相邻变化等轻量线索只能作为抽样优先级，不作为自动“角色完整 / 动作自然”的结论。初版无需为抽样新增重型视觉模型。

返工后优先抽样变更帧和邻帧，继续服从预算。问题量超过预算时报告覆盖情况和未观察范围，不假称全部修复帧都已视觉检查。技术检查仍全量，人工复审范围不受 AI 抽样预算限制。

### 9.3 自检记录

记录全帧技术检查计数与结果、采样帧及原因、实际观察到的问题、已执行修复、修复后结果、未解决项和未视觉覆盖范围。明确区分“自动检查通过”“抽样未发现问题”“用户确认通过”。

同类修复连续两次未改善或无法给出下一次具体改变时停止重复尝试，保存证据并提出必要问题；该值可作为任务预设配置。重试不会伪造批准、悄悄排除坏帧或补画不存在的源像素。

## 10. 验收工作台

在现有编辑 / 预览能力上增加统一验收视图，保留糖果主题、中文 / 英文 i18n、现有素材库与手工编辑入口。

必需交互：

- 显示候选版本、完整帧数、已确认 / 待确认 / 需修复计数，以及未解决问题。
- 以最终 PNG 为主要画面，切换源图、Alpha、黑 / 白 / 棋盘背景对照；显示像素尺寸和检查缩放。
- 保留左右键切帧、逐帧确认、撤销确认、跳转待确认 / 问题帧，以及按实际时长播放。
- 问题标注绑定帧 ID、候选和坐标系；区域以最终画布坐标记录。制作修复时由工具提供源坐标映射，不由 Skill 猜测笔刷坐标。
- 在返工候选中展示父候选对照、修复说明、实际影响范围和继承确认来源。
- 全部必要帧确认后，仍需用户明确记录整体播放验收；不由“最后一帧已确认”自动代替。
- 用户手工编辑时清楚进入制作副本；提交新候选后返回验收。

人类审核能力覆盖完整序列；联系表 256 缩略图限制不能限制逐帧读取。GUI 按需加载全序列，继续使用已有纹理预算和防过期切帧机制。

## 11. MCP / CLI 与服务接口

### 11.1 业务能力

| 能力组 | 需要的操作 |
| --- | --- |
| 发现 | 产品 / 生产协议版本、已支持能力、实际传输限制、schema、坐标定义 |
| 项目与输入 | 项目创建 / 查询、动作创建、视频 / PNG 导入；完整分页帧清单 |
| 制作 | 抽帧 / 抠图提交，帧 / 遮罩查看、修正 / 撤销，对齐保存，必要的显式时序变更 |
| 检查 | 全帧技术检查、采样清单 / 预览、制作状态与版本 |
| 协作 | 任务要求、候选提交 / 查看、审核反馈读取、修复问题与候选比较 |
| 交付 | 已接受候选打包、状态查询、产物 / 校验摘要 |
| 恢复 | 现有 job 查询 / 取消 / 恢复，加任务级续作位置 |

工具按业务操作设计，不因追求固定数量而合并含糊的行为。具体公开名称随实现计划确定，能力组和必需输入 / 输出在本文固定。

### 11.2 约束

所有修改带稳定目标 ID、预期内容修订 / 版本；冲突返回当前版本，不盲目重试旧参数。分页返回总数、游标和明确的完整性标志；大数组摘要明确标为摘要。

长任务立即返回 job ID；等待超时只表示客户端停止等待，不表示后台失败。导入视频 / 大 PNG 批次继续使用鉴权 multipart，MCP 查询使用同一源 ID。CLI 与 MCP 输出一致的结构化结果，日志不混入 JSON stdout。

对可能重复的创建、提交候选和交付操作使用幂等请求标识；请求相同标识但输入不同返回冲突。恢复先读已有任务 / 产物，再决定新建任务，不能重复整条处理链或覆盖旧结果。

恢复保留操作的原始输入身份和幂等标识；变更输入后的返工是新操作，不能通过丢弃旧 base revision 将“恢复”变成针对当前素材的隐式重跑。一次操作可关联多次执行尝试，但只能有一个经过校验的正式提交结果。

对抽帧提交、候选目录发布、交付目录发布等文件 / 数据库交界，保存带 operation ID 和哈希清单的提交检查点。服务重启先核对已提交产物、数据库状态和 job 结果：若文件已发布而结果尚未登记，补登记校验通过的结果；若只提交了片段 / 帧记录，读取提交身份并继续后续阶段。不能因 job 显示中断就重复抽帧、覆盖文件或把“已抽帧”当作新失败。

制作接口不暴露任意 shell、直接数据库写入、任意文件删除或云凭据设置。模型准备继续是明确下载 / 离线导入操作；Skill 不为完成任务隐式安装模型或更改全局 Codex 配置。

新能力在现有生产版本机制上升级到 1.2，MCP 返回真实产品版本与能力 schema 版本；CLI / 服务不兼容时返回明确版本冲突。旧 MCP / CLI 的人工审核操作不自动转换成新候选接受，新制作会话不能利用其绕过候选闸门。

动作首次进入协作流程时持久登记协作模式。该动作所有新正式导出入口都必须经过选定候选接受闸门，包括旧生产导出和其他保留的导出路径；省略 task ID / candidate ID 或调用旧入口不能退回遮罩批准规则。未进入协作模式的旧动作保留原人工流程，既有历史正式包仍可读取。协作任务取消不会自动取消该闸门。

## 12. 正式交付

接受条件：候选文件完整、全部必需帧已人工确认、整体播放已明确验收、无未解决阻断问题、全帧技术检查通过。

共享服务在 GUI 审核操作使当前任务选定候选满足全部条件时，以事务登记接受代次并提交唯一的打包操作。幂等键绑定 task ID、candidate ID 和接受代次；旧候选完成审核不会抢占当前任务的自动交付。`accepted → packaging` 由现有服务 / 队列执行，不等待 Codex 保持在线或额外发消息；Codex 后续读取结果，GUI 同步展示进度和产物。

正式交付以选定且已接受的固定候选为输入。复制已审核的最终 PNG 和固定图集，而非从不断变化的制作副本重新渲染；正式 manifest、审核引用和质量报告从同一候选生成。最终 PNG 字节、顺序、时长、画布与布局必须匹配候选清单。

生成 PNG 序列、规则图集、manifest、质量报告、联系表、背景预览 MP4、checksums 和 ZIP。质量报告保留“AI 视觉抽样”的事实，不将人工批准伪装成全帧 AI 视觉检查。

在打包前和发布前再次验证文件哈希与候选接受状态；采用新目录和完整发布，拒绝覆盖。取消或失败保留原件、旧成功版本和失败证据；未完整发布的结果不能标为已交付。取消接受会阻止正在打包的版本继续发布。

发布决定与撤销接受 / 新增阻断问题在同一服务临界区内串行处理。发布提交点再次验证当前选定候选、有效接受代次、最新审核状态和产物哈希，并持久记录发布操作 / 接受代次；只有提交成功才标记正式交付。文件目录存在而发布记录尚未提交，不能凭文件存在自动升级为正式包。崩溃恢复先重新验证接受代次，已失效的结果只保留为未发布证据。发布提交之后的撤销将该交付标为已撤回批准，保留历史文件；不悄悄删除已有产物。

现有 Cocos 锚点和导入说明继续兼容；本期不增加游戏工程自动修改或新的引擎导入器。背景 MP4 不作为透明素材。

### 13.1 组织与分发

升级现有 `skills/soldier-frame-studio/`，保留发行路径兼容；用户只需一个主要入口。公开描述明确用于本机 Sprite Motion Studio 的视频 / PNG 序列制作、返工与交付，保持正常自动发现，也支持用户主动调用。

建议结构：

```text

  SKILL.md
  agents/openai.yaml
  references/
    production.md
    review-and-rework.md
    recovery-and-delivery.md
```

入口包含任务要求、能力探测、制作 / 自检 / 提交 / 返工 / 交付路线和必要边界。详细坐标、错误恢复和 schema 使用按分支读取，不把完整接口目录重复粘贴到入口。

继续随便携包携带，提供简短使用与选择安装说明；不自动改用户全局配置。已有安装的版本匹配通过能力探测处理，不能假定发行文件名、项目 ID、默认工作区或模型已准备。

### 13.2 降低错误的具体做法

- 读取实际 `doctor` / capabilities / `schema`，根据工具当前能力调用；修正现有 `schemas` 拼写。
- 以已记录任务要求和预设为准，必要信息一次集中确认，不逐命令询问。
- 保持源帧与源时序，不自行减帧、原位覆盖原件或将草稿当正式输出。
- 修改前读取版本及坐标；冲突后重新查看状态，结合任务目标重新决定。
- 根据持久状态续作，不将等待超时当作任务失败，不重复创建已成功的动作 / 导出。
- 按采样预算读取图像，记录实际范围；全帧技术结果与人工确认分开。
- 返工对齐到具体问题和候选；完成判断必须基于实际返回值与产物校验。

如果重复逻辑需要确定性辅助脚本，优先放入产品 CLI / 服务；Skill 只调用现有实现，不复制图像处理、批准规则或另建制作链。

### 13.3 行为验证

Skill 完成前使用独立 Agent 做现实任务测试：先记录无新增指导 / 旧指导下的基线，再用新 Skill 重跑有意义的场景。评估 Agent 得到请求、Skill 和最小原始资料，不预告期望答案；使用隔离工作区，不写真实项目、不伪造真实人的验收。

至少验证：新工作区的最少输入任务、缺模型、长数组 / 大视频、等待超时后恢复、审核期间修改、源字节变化、局部返工、用户只说“导出”但未逐帧批准、抽样检查报告、隔离环境实际执行审核接口后的准确交付。测试中的审核身份不代表对真实素材的人工美术认可；格式检查不替代行为验证。

最少输入场景的通过标准：清晰单主体视频加一句目标，在已具备依赖 / 必需用途信息时，无须用户填写工作区 ID、画布、锚点、比例、recipe 或采样预算；所有推导 / 复用值有来源记录。有必要缺失项时最多一轮集中确认，不逐命令追问。PNG 缺时长的场景应集中取得确认的时长 / FPS，不凭空宣称源时序。

## 14. 兼容与实施分期

旧原件、完整抽帧、遮罩历史、成功导出和失败证据保留。旧项目仍可查看和编辑；旧遮罩批准不自动成为新候选最终帧批准。进入新协作流程时，从当前制作内容生成首个候选。

## 15. 验证与验收标准

| 场景 | 可验证的结果 |
| --- | --- |
| 超过 32 帧的输入 | 完整查询与技术检查覆盖全序列；采样只返回预算内图像；人工能逐帧访问全部帧 |
| 初稿未人工确认 | Codex 可继续制作、自检和提交候选；不能正式交付 |
| 人工确认操作 | 不改变候选像素或内容修订；重复确认不产生错误版本 |
| 局部修复 | 原候选不变；新候选正确列出变更 / 邻帧范围，未影响批准有可审计继承依据 |
| 地面轨迹 / 公共预设变化 | 识别插值区间和跨动作影响，拒绝复用失效批准 |
| 审核后外部改文件 | 完整性校验失败，拒绝发布，不以旧路径冒充旧内容 |
| 帧时长 / 顺序变化 | 输出反映明确任务要求，播放验收失效；源时序保持有理数 |
| 采样视觉检查 | 所选 ID / 理由 / 数量可复现，遵守预算，报告未覆盖范围 |
| 采样边界 | N=1 / 2 / 4 / 24 / 300 时 B=1 / 1 / 2 / 12 / 12；无风险时常规样本最多8，风险过多时按优先级截取并报告未覆盖项 |
| 检查到提交之间变化 | 拒绝公开与检查身份不一致的画面；重新生成并检查新版候选 |
| 发布 / 数据库登记之间中断 | 重启校验提交检查点并补登记已有结果，不重复抽帧或覆盖成功目录 |
| 打包期间撤销确认 / 新增阻断问题 | 审核修订冲突可检测，接受代次失效，发布提交点拒绝交付；重启不凭目录存在恢复为正式包 |
| 旧入口导出协作动作 | 同样要求候选接受；旧遮罩批准和省略候选 ID 不能绕过，新制作会话不能写人工批准 |
| 缺模型 / 超时 / 中断 | 说明具体依赖或读取已有 job 状态，不假成功、不重复制作链 |
| 只要求导出 | 不自动写入人工确认；返回当前待验收范围 |
| 接受后交付 | PNG 哈希、画布、顺序、时长和固定图集一致，全部校验通过后才报告已交付 |
| 手工编辑与旧项目 | 原件、既有导出可用；新候选不能冒用旧的遮罩批准 |

实现后按变更运行 Bun 测试、typecheck、Python 图像 Worker 测试及真实 GUI / CLI / MCP 闭环；测试批准使用隔离测试身份，不能写入用户项目。还需真实素材的人工美术验收，不能以机器检查或本机打包测试代替。

## 16. 风险与边界

视觉抽样可能漏掉未抽中的局部缺陷；最终人工逐帧审核承担完整覆盖。模糊、遮挡或不存在的源像素不能由遮罩修复恢复；提出补素材或明确接受缺陷，不自动补画。

候选保存最终帧会增加磁盘使用，优先引用已有不可变素材版本并避免重复渲染；自动清理不属于本期范围。公共角色预设和根轨迹插值扩大复审范围，影响计算不确定时保守扩大。

Skill 有助于稳定调用，但功能和批准边界必须有服务校验。独立行为测试与真实案例只能提供已观察的可靠性证据，不能证明所有素材和未来模型行为都不会出错。
