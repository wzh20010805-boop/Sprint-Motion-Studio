# 等待、恢复与交付

阶段提交后保存 operation/job ID，优先使用该调用返回的结果。超时后查一次原 `inspect_operation`／`get_job`：

| 实际状态 | 下一步 |
| --- | --- |
| 已成功并有完整结果 | 直接使用该原结果，进入未完成阶段 |
| queued/running | 在阶段边界继续等待，退避查询；不因客户端超时另建操作 |
| interrupted/failed 且操作支持恢复 | 检查具体错误与原输入，再 `resume_operation` 同一 operation |
| needs_input | 只解决返回的明确缺项；保留此前成功产物 |
| cancelled | 尊重取消状态；重新制作需新的明确意图 |

同一创建／固定／交付意图使用原 request_key 与原输入；409 冲突时读取当前身份，依据变更重新决定，不能删掉基础版本盲目重试。当前可持久恢复的操作是完整抽帧、固定候选和交付；协作 matting 的 `resume_supported:false/RECOVERY_UNSUPPORTED` 应照实处理。批量抠图先核对实际已完成帧／版本和失败原因，明确新的剩余范围及基础后再提交支持的任务；不宣称具有未实现的同操作恢复。

源路径相同也要验证当前字节身份；输入变更是新的制作意图。历史固定候选仍可有完整性证据，但不能自动代表当前被替换的源。保留原件、旧候选、失败尝试和旧成功包。

## 交付前的审核检查

开始交付时读取当前 task 和选定候选的 `review-state`，核对候选身份一致、`accepted` 为 true 且接受代次有效。这项检查同样适用于静态 PNG 动作；已有文件或素材已经透明不代表通过人工审核。未满足条件时执行 SKILL.md 的审核前边界，只提供审核入口与必要预览。

人工逐帧及播放通过后，服务自动为选定候选生成交付 operation。读取当前审核状态的 `pending_delivery_operation_id`，然后读取这项原 operation。`export_assets` 可以定位／排队已有接受版本，不能批准它。已接受但交付记录缺失时，报告该具体异常并按原操作恢复；不自行打 ZIP 补上，也不创建另一项“同样的导出”。

协作交付信息通过 `GET /api/v1/collaboration/deliveries/<operation ID>` 查询；以服务返回的实际 artifact URI／目录为准。核验候选与交付的全部最终 PNG、图集布局、顺序、画布、锚点和有理数时长，再核验 manifest、质量报告、checksums 和 ZIP。这些是完整技术核验，不能记成 AI 全帧视觉检查。预览 MP4 不含权威透明素材，也不替代逐帧及连续播放人工验收。

历史包被撤回批准时可保留并查看，但不能称为当前被接受的版本。正式发布前与最终交付说明前都核对当前接受／选定状态，防止使用过期缓存。
